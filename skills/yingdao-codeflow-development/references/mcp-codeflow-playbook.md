# CodeFlow MCP 开发手册

## 1. 预检与目标确认

修改前读取：

- 当前应用 ID、名称、活动流程和保存状态。
- 全部流程的 `flow_id`、类型和主流程标记。
- 当前资源文件，避免同名冲突或重复上传。
- 目标流程的参数和完整源码；源码分页时读到末尾。
- 必要时读取全局变量和 Python 依赖。

对任何修改都使用明确 `flow_id`。存在同名、多个候选流程或脏状态且无法安全绕开时，先确认目标。

### MCP 不可用时停止

- 工具未直接列出时，可以使用宿主提供的工具发现能力确认是否可调用；发现后仍无影刀 MCP 工具，或调用明确返回连接失败、服务不可用、传输超时，即按不可用处理，立即结束自动操作并请求用户恢复。
- 告知用户失败证据、已完成与未验证部分；有运行中的任务时保留 `run_id`，说明运行结果尚不确定。不要继续探测端点、扫描端口、修复隧道或切换 HTTP/curl、SSH、GUI、直接编辑应用文件等方案。
- 用户告知已恢复后再检查连接，读取实时工具 schema 并重新确认应用 ID、流程 ID 和保存状态；未完成的运行先核对原 `run_id`，不直接重跑。若仍不可用，立即反馈并停止。
- 区分连接故障与业务错误：字段校验或 Python 异常按正常调试处理；`app_run` 明确返回仍在运行的等待超时，按同一 `run_id` 继续等待，不视为连接不可用。

## 2. 流程与参数

- 新建代码流程使用 `app_create_flow` 且 `kind=code`。
- 用 `flow_write_parameters` 管理 In/Out 参数。集合参数使用 `type=any`，不要声明不存在的 `list` 或 `dict` 类型。
- 参数名应稳定、可读，并在描述中说明格式、默认值、是否允许为空和业务含义。
- CodeFlow 的入口保持为 `main(args)`；从 `args` 读取已声明输入，并把声明的输出写回相同名称。
- 参数默认值属于流程契约，测试样例属于测试配置；不要把两者混进代码常量。

### 命名与参数映射

- 遵循用户已有命名约定；未指定时，应用建议用“客户名-业务职责”（客户未知时只用业务职责），流程名表达业务用途，中文业务场景优先使用中文界面输入参数。说明参数类型、格式、必填性和空值含义；已有集成参数改名时先核对调用方。
- 建立紧凑映射表，逐项记录：入口输入及值来源 → `arguments.<参数名>` 实际值/变量 → 子流程 In 参数 → `args` 键名。没有主流程参数时，注明调用块的固定值来源；不得把普通文本变量名误当变量绑定。
- 中文化和参数改名同步修改声明、代码读取键名、调用字段及相关错误提示，回读确认；业务内部变量无需为界面中文化而整体重命名。
- 本次观察到 ShadowBot 6.3.9 / Python 3.7 在 `process.run` 中使用 CodeFlow 名构造结果类型名，全角括号导致 `namedtuple` 报错，静态检查未拦截。在该环境中，被调用 CodeFlow 名使用合法 Python 标识符形式（可含中文，避免括号、空格、连字符等，且非关键字）；应用显示名不受此条限制。其他版本以实际工具和运行证据为准，不将此问题推定为所有版本的限制。

## 3. 源码修改

- 新流程或大范围重构使用 `codeflow_write`，保证一次提交的完整源码可以通过 Python 语法校验。
- 小修改先使用 `codeflow_read` 获取当前内容；仅当旧文本唯一且修改局部时使用 `codeflow_edit`。
- `codeflow_edit` 匹配为零或多处时不要扩大替换范围，应重新读取并选择更稳定的修改边界。
- 使用 `glv` 时必须保留 `from .package import variables as glv`。
- 保留与任务无关的现有代码和用户修改；不要借重构删除未进入本次范围的行为。
- 错误信息应包含可行动的上下文，但不得泄露凭据或敏感数据。

## 4. 资源与依赖

- 添加资源前先列出现有资源；只加入运行或交付真正需要的文件。
- 添加后再次列出资源，并使用返回的应用内路径配置流程参数。
- 先用 `python_pip` 列出环境包，再决定是否安装。不要因为应用依赖清单为空就断定运行环境没有该包。
- 安装或卸载依赖属于应用变更；仅对需求所需包执行，并在交付中记录。

## 5. 主流程调用

当需要主流程入口时：

1. 在调用方 VisualFlow 中使用 `process.run`，不得让流程调用自身。
2. 先确认子流程参数列表和目标 `flow_id`。
3. 填写 `process` 后，只使用返回表单中的 `arguments.<参数名>` 字段传入参数。
4. 参数需要固定测试值或默认值时显式填入；复查块详情中是实际 `value`，而不只是界面提供的 `default`。
5. 子流程输出使用 `output_properties.process_result` 返回的精确引用表达式，不自行猜测引用路径。

复制、重命名或重新选择调用目标后，重新读取流程列表、目标参数和调用块详情。流程 ID 可能改变，重新设置 `process` 也可能清空已有参数；用更新后的表单逐项补齐映射，再保存回读。检查所有受影响调用方，不假定工具会自动保留绑定。需要副本时明确复制的是应用还是流程，记录新旧入口和目标，避免混用。

主流程只负责必要编排；数据处理、算法和复杂业务规则仍由 CodeFlow 负责。

## 6. 验证闭环

1. 使用 `app_save` 保存并编译。
2. 使用 `diagnostics_snapshot` 检查全部静态错误和最近运行异常。
3. 保存后回读调用块，逐项核对必填输入的实际 `value` 或有效变量绑定、上游值来源和可选空值含义。有主流程交付入口就以其明确 `flow_id` 调用 `app_run` 验收；只跑子流程不足以完成交付。该调用不接受临时业务入参；测试值应来自流程默认值或调用方 `process.run` 的显式参数。
4. 若运行已经返回终态，直接使用该结果；不要再调用等待或结果接口。
5. 只有运行超时时，才用原 `run_id` 调用 `app_wait_run_finish`；不得重新运行代替等待。
6. 用户暂停或停止运行时立即停止自动操作并询问下一步。
7. 运行成功后核验 `result.outputs`、日志和实际业务产物。主流程未声明 Out 时不能仅凭空结果判断子流程成败；读取指定主流程的变量快照，核对实际输入、调用结果和子流程输出。需要向外暴露结果时显式声明并承接 Out。

最终记录实际运行的流程、参数来源、输出、处理数量、产物路径、未验证分支和任何人工步骤。

### 配置、产物与交付证据

- 记录当前配置用于验收样例还是正式业务，以及目标期间、输入来源、可选工作表、输出目录和替换方式。授权保留的可运行样例配置不要在验收后清空；样例通过只证明覆盖范围，不能声称真实业务数据已验收。
- 文件产物不仅检查存在，还要读取关键内容。表格类按需求核对工作表、处理行数、关键明细、金额汇总与勾稽关系、异常数量；例如收入分摊应核对收入、净收款、期初余额与期末结转。
- 链接直接使用实际输出路径，禁止手工重拼文件名。开发机与运行机路径不同时，只在核实共享目录映射后转换为本地绝对路径并检查存在；不能核实就如实提供运行机路径。
- 分别报告引擎执行状态、业务验收结果、发布/人工复核状态。引擎成功不代表没有业务异常，也不代表允许发布。
- 参数绑定、调用目标或运行相关名称变更后重跑交付入口；业务逻辑变更覆盖相关验收案例和异常分支。仅修改应用显示名称，回读名称和保存状态即可，不为低影响元数据变更重复业务运行。
