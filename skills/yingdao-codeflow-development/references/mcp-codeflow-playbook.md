# CodeFlow MCP 开发手册

## 1. 预检与目标确认

修改前读取：

- 当前应用 ID、名称、活动流程和保存状态。
- 全部流程的 `flow_id`、类型和主流程标记。
- 当前资源文件，避免同名冲突或重复上传。
- 目标流程的参数和完整源码；源码分页时读到末尾。
- 必要时读取全局变量和 Python 依赖。

对任何修改都使用明确 `flow_id`。存在同名、多个候选流程或脏状态且无法安全绕开时，先确认目标。

## 2. 流程与参数

- 新建代码流程使用 `app_create_flow` 且 `kind=code`。
- 用 `flow_write_parameters` 管理 In/Out 参数。集合参数使用 `type=any`，不要声明不存在的 `list` 或 `dict` 类型。
- 参数名应稳定、可读，并在描述中说明格式、默认值、是否允许为空和业务含义。
- CodeFlow 的入口保持为 `main(args)`；从 `args` 读取已声明输入，并把声明的输出写回相同名称。
- 参数默认值属于流程契约，测试样例属于测试配置；不要把两者混进代码常量。

## 3. 源码修改

- 新流程或大范围重构使用 `codeflow_write`，保证一次提交的完整源码可以通过 Python 语法校验。
- 小修改先使用 `codeflow_read` 获取当前内容；仅当旧文本唯一且修改局部时使用 `codeflow_edit`。
- `codeflow_edit` 匹配为零或多处时不要扩大替换范围，应重新读取并选择更稳定的修改边界。
- 使用 `glv` 时必须保留 `from .package import variables as glv`。
- 保留与任务无关的现有代码和用户修改；不要借重构删除未进入本次范围的行为。
- 错误信息应包含可行动的上下文，但不得泄露凭据或敏感数据。

## 4. 资源与依赖

- 添加资源前先列出现有资源；只加入运行或交付真正需要的文件。
- 添加后再次列出资源，并使用返回的应用内路径配置流程参数。
- 先用 `python_pip` 列出环境包，再决定是否安装。不要因为应用依赖清单为空就断定运行环境没有该包。
- 安装或卸载依赖属于应用变更；仅对需求所需包执行，并在交付中记录。

## 5. 主流程调用

当需要主流程入口时：

1. 在调用方 VisualFlow 中使用 `process.run`，不得让流程调用自身。
2. 先确认子流程参数列表和目标 `flow_id`。
3. 填写 `process` 后，只使用返回表单中的 `arguments.<参数名>` 字段传入参数。
4. 参数需要固定测试值或默认值时显式填入；复查块详情中是实际 `value`，而不只是界面提供的 `default`。
5. 子流程输出使用 `output_properties.process_result` 返回的精确引用表达式，不自行猜测引用路径。

主流程只负责必要编排；数据处理、算法和复杂业务规则仍由 CodeFlow 负责。

## 6. 验证闭环

1. 使用 `app_save` 保存并编译。
2. 使用 `diagnostics_snapshot` 检查全部静态错误和最近运行异常。
3. 使用明确 `flow_id` 调用 `app_run`。该调用不接受临时业务入参；测试值应来自流程默认值或调用方 `process.run` 的显式参数。
4. 若运行已经返回终态，直接使用该结果；不要再调用等待或结果接口。
5. 只有运行超时时，才用原 `run_id` 调用 `app_wait_run_finish`；不得重新运行代替等待。
6. 用户暂停或停止运行时立即停止自动操作并询问下一步。
7. 运行成功后核验 `result.outputs`、日志和实际业务产物。子流程内部结果不会自动成为主流程声明输出，需要显式承接。

最终记录实际运行的流程、参数来源、输出、处理数量、产物路径、未验证分支和任何人工步骤。
