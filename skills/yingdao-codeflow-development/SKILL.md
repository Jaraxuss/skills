# 影刀 CodeFlow 规范开发

把开发就绪的需求实现为可运行、可测试、可交付的影刀 CodeFlow，并保留必要的主流程调用入口。

## 开始前

1. 确认用户已授权修改当前影刀应用，并取得需求文档或等价的输入、输出、规则、异常及验收契约。关键歧义会改变结果时先确认，不要在代码中猜测。
2. 阅读 [CodeFlow MCP 开发手册](references/mcp-codeflow-playbook.md)。
3. 通过 MCP 读取当前应用信息、流程列表、资源、目标流程参数及已有源码。不要依赖界面焦点猜测当前目标，也不要覆盖无关或用户已有修改。
4. 一旦确认影刀 MCP 不可用，立即停止操作并告知用户、请求恢复。不要反复探测，也不要改用 HTTP/curl、SSH、端口转发、GUI 或直接改应用文件等替代方案；恢复后的核对见开发手册。

## 实现流程

1. 复用合适的现有 CodeFlow，或创建 `kind=code` 的新流程。流程名应表达业务职责，避免使用“测试”“流程1”等临时名称。
2. 先声明稳定的 In/Out 参数契约，再编写代码。代码通过 `args` 读取输入和写入声明的输出；测试路径、账号和样例值不得硬编码进业务逻辑。
3. 用资源接口加入需求文档和运行必需的模板或样例；代码引用应用内资源路径，不假设开发机原始路径在其他环境仍存在。
4. 仅在确有需要时检查或安装 Python 依赖。优先使用环境已有依赖，并保持依赖最小化。
5. 新建或整体重构时写入完整源码；小范围修改前先读取源码，并只对唯一匹配内容使用精确编辑。
6. 用户需要统一入口时，让主 VisualFlow 只承担编排或 `process.run` 调用；业务逻辑仍留在 CodeFlow。建立入口输入、调用字段、子流程参数和 `args` 键名的映射；复制、改名或切换调用目标后重新回读并补齐绑定。
7. 保存编译、检查诊断、运行目标流程并核验声明输出和业务产物。运行超时时等待同一 `run_id`，不得仅为获取结果而重新运行。

## 完成标准

- CodeFlow 源码、流程参数、资源和依赖与需求一致。
- 静态诊断无错误，运行结果得到明确验证；仅有“已保存”不等于完成。
- 有主流程交付入口时，必须保存后回读调用块的必填输入实际值或变量绑定，并从主流程运行验收；只跑子流程不能宣布交付完成。
- 应用和界面参数按使用者语言命名；验收配置与正式配置用途明确。按手册核验产物内容，区分引擎成功、业务验收和发布状态。
- 测试没有覆盖的分支、需要真实账号或人工确认的步骤已明确说明。
- 交付摘要列出流程名、输入默认值、输出、资源、测试结果和产物位置。

## 边界

- 不把 CodeFlow 请求改造成由大量 VisualFlow 指令承载业务逻辑。
- 不为了测试而修改业务规则或把默认测试值写进源码。
- 不自行执行超出需求范围的外部提交、删除、发送或生产写入。
- 用户只要求分析或诊断时，不顺带实现修复。
