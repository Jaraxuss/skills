# VisualFlow MCP 开发手册

## 1. 预检与流程设计

修改前读取：

- 当前应用信息、保存状态和活动流程。
- 全部流程的 `flow_id`、类型、主流程标记及块数量。
- 目标流程参数、现有指令块详情、可见变量和必要资源。
- 涉及网页或应用操作时，需求中指定的选择器和目标系统前提。

按实际业务执行顺序设计流程。只有多个相邻步骤互不依赖且工具支持安全批量操作时才批量修改；不要为了减少调用而牺牲块顺序和作用域正确性。

### MCP 不可用时停止

- 工具未直接列出时，可以使用宿主提供的工具发现能力确认是否可调用；发现后仍无影刀 MCP 工具，或调用明确返回连接失败、服务不可用、传输超时，即按不可用处理，立即结束自动操作并请求用户恢复。
- 告知用户失败证据、已完成与未验证部分；有运行中的任务时保留 `run_id`，说明运行结果尚不确定。不要继续探测端点、扫描端口、修复隧道或切换 HTTP/curl、SSH、GUI、直接编辑应用文件等方案。
- 用户告知已恢复后再检查连接，读取实时工具 schema 并重新确认应用 ID、流程 ID 和保存状态；未完成的运行先核对原 `run_id`，不直接重跑。若仍不可用，立即反馈并停止。
- 字段校验或业务执行异常按正常调试处理；`app_run` 明确返回仍在运行的等待超时，按同一 `run_id` 继续等待，不视为连接不可用。

## 2. 发现指令原型

- 在插入指令前读取影刀 MCP 提供的 `knowledge/visual-blocks/block_catalog.md` 和相关 `block_detail.md`，或使用 Wiki 搜索定位对应指令文档。
- 使用文档中的准确 `prototype_name`。不要按中文指令名称、记忆或相似功能猜测原型。
- 需要选择器时，优先使用需求或现有流程给出的准确名称。仅在名称未知时使用选择器列表做字面过滤；零结果或多个候选都应停止猜测并询问用户。
- 指令设置界面依赖账号、工作簿或其他动态数据时，使用插入结果中的 `dynamic_data_for_llm` 候选及其成组字段，不拆开拼接不兼容值。

## 3. 插入与填写

- `flow_edit_blocks` 是插入和删除指令实例的唯一入口。插入时提供执行位置、准确原型和简短英文语义标签；该标签用于本次块映射，不会成为 Studio 中的持久注释。
- 插入操作只创建块，不填写设置。使用返回的 `block_id` 调用 `flow_fill_blocks`。
- 普通字段放入 `fills`，同一块在一次调用的 `fills` 中只出现一次。
- 重复结构字段使用顶层 `group_fills`；共享字段放 `fixed`，变化字段放等长的 `columns` 数组。
- 普通字符串表示字面量；空字符串使用显式文本形式。变量、表达式、选择器、数组和对象使用对应语义包装，不把变量名当普通文本填入。
- 长多行代码或文本直接传字符串，不套只为显式空文本设计的包装。
- 一个块填写失败不代表整批都失败。检查 `fill_errors`，仅重试失败的 `block_id`；`validation_errors` 是当前流程整体遗留问题，应单独处理。

## 4. 变量、参数和作用域

- 填写变量引用前使用 `flow_list_variables` 检查变量名、来源、定义位置和可见范围。
- 循环、条件、异常处理内部变量不能逃逸到外部；需要跨作用域使用时，在合法外层建立明确输出或赋值。
- 用 `flow_write_parameters` 管理流程参数。集合使用 `type=any`。
- VisualFlow 的计算型 Out 参数不要设置初始化值；产生它的块输出必须与 Out 参数同名。
- 代码片段中创建的变量无法被静态作用域分析识别，因此不要让关键数据契约依赖隐藏变量。

### 命名与参数映射

- 遵循用户已有命名约定；未指定时，应用建议用“客户名-业务职责”（客户未知时只用业务职责），流程名表达业务用途，中文业务场景优先使用中文界面输入参数。说明类型、格式、必填性和空值含义；已有集成参数改名时先核对调用方。
- 建立紧凑映射表：入口输入及值来源 → `arguments.<参数名>` 实际值/变量 → 子流程 In 参数 → 消费该参数的块字段；若被调用方是 CodeFlow，最后一项为 `args` 键名。固定值和可选空值也需注明来源与含义。
- 中文化或参数改名同步修改声明、消费位置、调用字段及相关错误提示，检查执行顺序和变量作用域；业务内部变量不必全部重命名。
- 本次观察到 ShadowBot 6.3.9 / Python 3.7 在调用 CodeFlow 时用其名称构造结果类型名，全角括号导致 `namedtuple` 报错且静态检查未拦截。在该环境中，被调用 CodeFlow 名使用合法 Python 标识符形式（可含中文，避免括号、空格、连字符等，且非关键字）；不把该限制套用于应用显示名，也不推定所有版本或 VisualFlow 都有同一缺陷。其他情况按运行证据验证。

## 5. 子流程调用

使用 `process.run` 时：

1. 调用方和目标流程必须不同，避免递归调用。
2. 先确认目标流程的 In/Out 参数；设置 `process` 后，以更新表单中的字段为准。
3. 只通过 `arguments.<参数名>` 填入子流程输入。
4. 使用 `output_properties.process_result` 中返回的精确表达式引用子流程输出；`outputs` 只保存承接结果的变量名。
5. 复制、重命名或重新选择目标流程后，重新读取流程列表、目标参数和调用块详情；流程 ID 可能改变，设置 `process` 也可能清空绑定。按新表单逐项补齐映射，检查所有受影响调用方，再保存回读，不沿用旧目标字段或假定绑定自动保留。需要副本时明确复制的是应用还是流程，记录新旧入口与目标。

## 6. 验证与调试

1. 修改后用块详情复查顺序、原型、字段实际值和输出变量。
2. 使用 `app_save` 保存并编译，再用 `diagnostics_snapshot` 处理静态错误。
3. 保存后回读必填输入的实际 `value` 或有效变量绑定、上游值来源和可选空值含义。有主流程交付入口时，用其明确 `flow_id` 调用 `app_run` 验收；只跑子流程不足以完成交付。运行返回终态时直接使用结果；仅在等待超时时用同一 `run_id` 等待。
4. 用户暂停或停止时立即停止自动操作并询问下一步。
5. 运行失败时先读取诊断和日志；需要块级输入输出时，再读取目标 VisualFlow 的变量快照。
6. 修复应针对证据指向的问题，不通过重复运行碰运气，也不重写无关块。

最终核验流程输出、页面或文件副作用、重复执行行为、异常路径和人工介入点，并记录未能在当前环境验证的步骤。

### 配置、产物与交付证据

- 记录当前配置用于验收样例还是正式业务，以及目标期间、输入来源、可选工作表、输出目录和替换方式。授权保留的可运行样例配置不要在验收后清空；样例通过只证明覆盖范围。
- 成功运行后读取交付入口的变量快照，确认实际输入、调用结果与子流程输出。主流程没有声明 Out 时，聚合结果可能为空，应以快照和产物验证；需要向外暴露结果时显式声明并承接 Out。
- 文件产物不仅检查存在，还要读取关键内容。表格类按需求核对工作表、行数、关键明细、汇总与勾稽关系及异常数量；例如收入分摊应核对收入、净收款、期初余额与期末结转。页面操作按需求核验实际页面状态或业务记录。
- 链接直接使用实际输出路径，禁止手工重拼文件名。跨运行机与开发机的路径只在核实共享目录映射后转换为本地绝对路径并检查存在；不能核实就如实提供运行机路径。
- 分别报告引擎执行状态、业务验收结果、发布/人工复核状态；运行成功不等于业务无异常或允许发布。
- 参数绑定、调用目标或运行相关名称变更后重跑交付入口；业务分支变更覆盖相关验收案例和异常路径。仅修改应用显示名称时回读名称和保存状态即可，不重复业务运行。
