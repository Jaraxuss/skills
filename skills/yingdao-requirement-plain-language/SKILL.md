# 需求说人话

帮助教练把自己理解的业务讲清楚，让客户能照着学习如何向影刀 AI 流程助手提需求。课前可详细分析材料、澄清规则、试跑；课堂从一段自然的业务描述开始，再在影刀里搭建、检查和修改。

本 Skill 的交付物是一段可复制的课堂需求，以及确实需要时附上的最小材料清单。默认不生成完整需求文档、不实现业务、不调用影刀 MCP。用户另行要求开发或试跑时，按相应工作流处理，并据实报告验证结果。

## 先复用已知业务

- 优先使用当前聊天中已经确认的流程、规则、附件和最新决定，不要求用户重新讲一遍，也不把完整需求文档作为前置条件。
- 用户给了原始录屏、转写、沟通或样例时，先完成足够理解业务的梳理；不为了写短需求而默认生成一份长文档。客户聊天和会议原文的检索使用可用的 `customer-communication-knowledge`，用户指定本地材料时可直接读取。
- 分清本期做什么、后续人工做什么，以及哪些旧规则已被用户排除。单次样例数据、历史备注和技术猜测不能自行升级为业务规则。
- 发现会改变数据范围、金额、外部提交或最终产出的关键缺口，向教练提出最少的必要问题。能继续时先给可用部分，并将缺口简短放在课堂正文外；也可在正文保留“遇到这种情况先提示我确认”的实际处理边界，不编造默认答案。
- 只有相关证据可用时才判断案例是否已试跑、适合直接演示。材料理解、静态核算和流程成功运行分别说明，不承诺未验证的产品能力。

## 写成业务人员会说的话

先抓住四件事：**要做什么、给哪些输入、人工怎么做、最后要什么结果**。用“帮我做……”“先……再……”“这一步我们人工处理”等自然表达，省去铺垫和技术规格口吻。

- 默认以一屏左右为目标，通常约 200–500 个汉字。复杂业务可稍长；用户要求更短时优先合并步骤、减少重复。不要为了固定字数删掉影响正确性的规则，也不要机械凑步骤数。
- 输入只交代现有附件各有什么用，以及每次需要填写的日期、目录等参数。没有的文件不能写成“我已提供”；可先制作必要模板，但须有用户授权并实际完成。
- 规则能从附件清楚读出时写“按附件里的整理说明筛选”，不再全文抄写。决定方向的例外仍需留下，例如“只保留”与“删除”的区别、跨月分段、负数保留、字段来自哪个业务系统。
- 输出写清格式、关键字段对应、命名或保存要求；仅保留本场景确实需要的程度。业务边界用一句话交代，如“导入内部系统由我们人工做”。
- 不写需求编号、验收矩阵、状态机、变量类型、DOM 选择器或实现算法。开发模式和具体指令未确认时留给助手选择，不把某次案例采用可视化模式当成通用要求。
- 不堆“请充分理解、确保鲁棒性、严格遵守”等套话，不罗列全套技术异常。将必要情况说成具体动作，例如“找不到对应规则就先提醒我”。
- 不用错别字、含糊表达或故意遗漏模拟“人写”。简短描述必须忠于已确认业务；不编造作者经历、现场发现过程或已经完成的验证。

## 交付方式

默认直接给一段 `text` 代码块，内容可原样粘贴到影刀 AI 流程助手。目标、输入和操作步骤可自然连写，简单场景不用强套标题。课前附件清单仅在有必要时放在块外，每个文件用一句话说明用途。

课堂正文里的文件名应便于客户识别；本地可点击路径放在块外。不要把 Codex 当前机器的绝对路径当作客户 Windows 的运行路径，也不要在正文抄密码。

用户只说“再精炼”“更像人话”时，直接改写上一版，不重复调研、不附长篇解释、不再输出多个候选版本。示例语气及压缩取舍见 [references/examples.md](references/examples.md)，需要参考时再读。

交付前快速检查：客户看完能否照着自己写；输入是否真实存在、用途清楚；关键规则是否仍在正文或已提供的附件中；是否把技术细节、缺失规则或旧决定混进去了。无需另写自查报告。
