# 资料分析与成文规则

## 1. 证据登记

先按来源记录可用资料及其用途：

- 用户在当前对话中的明确要求：定义本次任务范围和最新决策。
- 现场录屏、录音或转写：用于还原操作过程、角色表达和业务语境。
- 沟通截图：用于确认页面状态、字段、示例和补充决策。
- 样例数据：用于确认真实结构、类型、值域、公式、空值和边界情况。
- 历史文档或旧流程：用于理解背景，不自动代表当前要求。

当来源冲突时，记录冲突，不自行选择对业务结果影响重大的解释。最新的用户明确确认优先于较早材料，但不得悄悄覆盖历史差异，应在文档中留下决策说明。

## 2. 四类结论

每个重要结论都应属于以下一类：

- 已确认事实：有明确证据或用户确认。
- 合理推断：从多个证据得到，但尚未被明确确认。
- 待确认项：缺失信息会改变实现或验收结果。
- 冲突项：不同来源给出不兼容说法。

不要为了让文档看起来完整而消除后三类内容。

## 3. 开发所需信息

需求文档至少覆盖：

- 业务目标、使用角色和触发方式。
- 自动化边界、明确不做的事项以及外部系统副作用。
- 输入文件、页面、数据表、参数和必要凭据的来源。
- 输出文件、页面写入、返回参数、命名和保存规则。
- 主流程、关键判断、循环、数据转换及状态变化。
- 异常、空数据、重复执行、部分成功、重试和人工介入方式。
- 数据保真要求，如是否保留原文件、格式、公式、顺序和审计痕迹。
- 可验证的验收标准和最少一组正常、边界、异常测试样例。

对 UI 自动化，还应记录目标应用、页面入口、稳定识别信息、登录前提和需要人工确认的动作。对数据处理，还应记录字段映射、计算公式、精度、去重键、时间口径和幂等性。

## 4. 模式建议

模式建议只用于交接：

- CodeFlow：复杂数据处理、文件加工、算法、接口调用或大量结构化逻辑更适合代码表达。
- VisualFlow：页面操作、标准指令串联、需要业务人员直接查看和维护的步骤更适合可视化表达。
- 混合模式：允许主流程或编排流程调用子流程，但必须说明每个流程的职责；不要用模式选择掩盖尚未确认的业务规则。

## 5. 开发就绪门槛

以下内容明确后，才称为“可直接开发”：

- 输入、输出和关键参数有清晰契约。
- 核心处理规则可以转写为无歧义步骤或公式。
- 外部写入、提交、删除等副作用已获得相应授权。
- 主要异常和重复执行策略已说明。
- 验收结果可观察、可比较。

若未达到门槛，文档仍可交付为需求草案，但必须明确阻塞开发的待确认项。
